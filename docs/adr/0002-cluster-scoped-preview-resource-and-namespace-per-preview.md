# 2. One namespace per preview, owned by a cluster-scoped resource

- Status: accepted
- Date: 2026-10-28

## Context

Previews of different pull requests must not see each other: not their database, not their secrets, not
their traffic. They also must not starve each other or the rest of the cluster.

## Decision

- Each preview gets its own namespace, `pr-<number>`, with Pod Security `restricted`, a ResourceQuota, a
  LimitRange, and NetworkPolicies that deny everything except DNS, the ingress controller to the API, the
  platform's pods to their own database, the API to the OpenTelemetry collector, and the deployment Job to the
  Kubernetes API. The local environment of `devctl up` is pull request 0, namespace `local`.
- `PreviewEnvironment` is cluster-scoped. A namespaced resource cannot own the namespace it would live in, and
  a cluster-scoped owner lets Kubernetes' garbage collector delete the namespace when the resource goes.
- The database is a PostgreSQL StatefulSet inside the namespace, on an `emptyDir`. Preview data is synthetic
  or pseudonymised and lives as long as the preview, so losing it with the pod is a feature.
- Credentials are generated by the operator when the namespace is created, and never leave it. The API gets a
  role with data-only privileges. Migrations run with the owner role.

## Consequences

- Isolation does not depend on application code: a bug in the API cannot reach another preview's database,
  because the network refuses the connection.
- A preview costs one PostgreSQL pod. Fine for tens of previews. Hundreds would call for a shared database
  server with one database per preview.
- The operator needs cluster-wide permission to create namespaces, and nothing else cluster-wide. Everything
  inside a preview namespace is granted by a RoleBinding the operator creates there.

## Alternatives considered

- **Shared namespace with name prefixes.** Cheaper, but NetworkPolicies and quotas become per-label puzzles,
  and one preview's runaway pod can still exhaust the namespace's quota for all of them.
- **vcluster per preview.** Stronger isolation (each preview gets its own API server), at the price of a
  control plane per pull request. Worth it when previews must install CRDs or cluster-wide resources, which
  this API does not.
